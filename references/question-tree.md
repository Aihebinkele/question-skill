# 议题树与提问卡参考

`反向提问` 的 Step 1 / Step 2 素材库。议题树给出**依赖顺序**（先问上游），提问卡给出**措辞对照**（怎么问才有效）。

> [!tip] 用法
> 先挑一棵最接近的树，删掉已经能从文件/代码/历史对话里查到的节点，剩下的就是 frontier。树只是起点，不是问卷——不要逐条问完。

> [!important] 提问卡骨架不可省
> 无论用哪棵议题树、给不给选项，每轮都必须保留 `反向提问` 的三件套：**当前理解（复述）/ 追问（一个问题）/ 置信度（百分比且逐步上调）**。本文件的示例是措辞参考，不是替换格式。

---

## 1. 软件 / 工具开发

```
目标用户 → 核心痛点 → 形态(CLI/GUI/Web/脚本) → 运行环境与栈
        → 数据来源与存储 → 与现有系统的集成点 → 明确不做 → 验收标准
```

| 议题 | 典型追问 |
|------|----------|
| 目标用户 | "是给你自己用，还是给别人用？他们现在怎么做这件事？" |
| 核心痛点 | "现在最烦的是哪一步？慢、容易错、还是根本没人做？" |
| 形态 | "每天用几次？一次用 5 分钟还是半小时？"（决定 CLI vs GUI） |
| 集成点 | "需要读写现有哪个系统/文件？有 API 还是只能读文件？" |
| 明确不做 | "这版明确不做什么？"（比问"还要做什么"更能收窄范围） |

## 2. 文档 / PPT / 汇报材料

```
目的(听懂什么/决定什么) → 场合(现场讲/自阅) → 受众(专业度)
→ 必保内容与必删内容 → 风格与品牌 → 交付形态 → 篇幅
```

| 议题 | 典型追问 |
|------|----------|
| 目的 | "听众看完要做什么决定？"（决定标题是不是结论句） |
| 场合 | "站着讲还是发出去自己看？"（决定信息密度） |
| 受众 | "他们懂这个领域吗？哪些术语不用解释？" |
| 必保/必删 | "哪些结论和数字必须留下？哪些是凑数的？" |

## 3. 数据分析 / 建模 / CAE 任务

```
要回答的问题 → 数据/模型来源与可信度 → 精度要求 → 边界条件与假设
→ 计算资源与时限 → 结果怎么用 → 验收标准
```

| 议题 | 典型追问 |
|------|----------|
| 要回答的问题 | "这份结果是用来支持哪个判断？" |
| 数据可信度 | "数据谁给的？有没有标定或实验对照？" |
| 精度要求 | "误差 5% 够用吗？还是必须和试验对上？" |
| 结果怎么用 | "结果交给谁？他会拿它做什么决定？" |

> [!warning] 建模类任务
> "网格多细""用哪个求解器"是**下游**问题。上游没定（要回答什么、精度要求多少）就问这些，会让用户以为你在炫技，实际是在猜。

## 4. 自动化 / 脚本 / 批处理

```
输入从哪来 → 触发方式(手动/定时/事件) → 失败怎么办 → 输出到哪
→ 谁来维护 → 可观测性(日志/通知)
```

| 议题 | 典型追问 |
|------|----------|
| 失败处理 | "中途失败，是重跑全部还是断点续跑？" |
| 输出 | "结果发飞书、写文件，还是只打日志？" |
| 维护者 | "三个月后是谁来改它？"（决定注释与配置外置程度） |

## 5. 采购 / 选型

```
真实需求 → 预算与时间窗 → 硬性门槛 → 可选项权重 → 退出成本 → 决策人
```

| 议题 | 典型追问 |
|------|----------|
| 真实需求 | "没有它，现在这件事是怎么完成的？" |
| 硬性门槛 | "哪一条不满足就直接排除？" |
| 退出成本 | "用一年想换掉，迁移要多久？" |

## 6. 生活 / 个人事务

```
要解决什么 → 时间与精力预算 → 不可妥协项 → 最坏后果 → 谁受影响
```

| 议题 | 典型追问 |
|------|----------|
| 不可妥协项 | "哪些条件满足不了，这事就不做？" |
| 谁受影响 | "这个决定还要谁同意或配合？" |

## 提问卡：好 vs 坏

### 坏 1：填空题

> 你想要什么风格？

用户答不出，只能回"好看一点"。

### 好 1：三选一 + 后果

> 这份材料最影响观感的一个选择是**信息密度**：
>
> - A. 现场讲，每页一个结论（推荐）——细节进备注，讲的时候你不会被页面带着走
> - B. 发出去自阅，每页自带论据——没有你讲解，页面必须自洽
> - C. 两者都要——按现场讲做，另附一页附录
>
> **为什么问这个**：它决定后面每页是"金句 + 留白"还是"标题 + 三段论据"，改起来是整份重排。

### 坏 2：问能查到的

> 你的项目用的是什么技术栈？

（README / package.json / 目录结构里明明有。）

### 好 2：先查再问真正查不到的

> 我看了 `package.json`，是 Vite + React 18（已锁定，不再问）。真正卡住的是**部署形态**：这是只在自己电脑上跑，还是要给同事访问？

### 坏 3：假选项

> - A. 用 React
> - B. 用 React + TypeScript
> - C. 用 React + TypeScript + Vite

三个选项是同一个方向，用户没有真正的选择。

### 好 3：互斥且含反向

> - A. 纯前端，数据存本地（推荐）——一天上手，但换电脑数据要手动搬
> - B. 前端 + 轻后端，数据进数据库——多人可用，但要多维护一个服务
> - C. 先不做工具，用现成表格 + 脚本过渡——两周能验证需求真假，代价是以后要重做

### 坏 4：开放式硬凑选择题

> 请选择你的使用场景：A. 早上 B. 中午 C. 晚上

场景不是时段，选项答非所问。

### 好 4：开放题就开放问

> 能描述一次你最近真正用到它的场景吗？从打开电脑开始，到事情做完为止。

## 收口检查

问完后回看决策台账，逐条确认：

- 每条结论的**依据**是"用户确认 / 我的推荐 / 自行查证"三者之一，没有空着。
- 没有一条结论是"用户没表态、我就当默认同意了"却没写进「我做过的假设」。
- 「待确认」里的每一条都写了**默认怎么处理**，而不是留给用户一个空问题。
